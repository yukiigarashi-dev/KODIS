# 監査ログのチェックポイントと残るリスク

KODIS の監査ログ（`internal/audit`）は、ハッシュチェーンの JSON Lines ファイルです。チェーンの検証だけでは「末尾のレコードを丸ごと削除する」改ざんを検出できないため、外部に保管するチェックポイントで補います。この文書は、その設計と、それでも残るリスクをまとめたものです。

## ID の区別

| ID | 意味 | どこにあるか |
|---|---|---|
| log_id | ログ自体の識別子。初期化レコード（seq 1）のハッシュ | チェックポイント、`audit-init` / `audit-recover` の出力 |
| tenant_id | ログのスコープ。初期化レコードに記録する | 初期化レコード。`run` は設定の tenantId と一致しなければ拒否する |
| target_id | Action ごとの変更対象（ポリシー ID） | Plan と監査記録。チェックポイントやスコープには含めない |

初期化レコードには32バイトの乱数（nonce）を含めます。CLI は `crypto/rand` を使うので、同じテナント・同じ時刻でログを作り直しても、log_id は実質的に重複しません。ただしこれは確率的な保証です。同じ乱数・時刻・テナントを与えれば、同じ log_id になります（テストでは乱数を注入して、この性質を確かめています）。

## チェックポイント

形式: `kodis-ckpt/v1:<log_id>:<seq>:<head_hash>`

- **作成するとき**: `kodis audit-init`、`kodis run`、`kodis audit-recover` が、実行の最後にチェックポイントを表示します。
- **保存しない**: kodis はチェックポイントを自分では保存しません。保管するのは運用者です。
- **照合するとき**: `kodis run -checkpoint ...` は、ログに何かする前に次を確かめます。照合の結果は、成功・失敗のどちらでも `checkpoint` レコードとして記録します。
  1. チェーン全体が正しい
  2. 照合結果: log_id が一致し、seq 番目のレコードのハッシュが head_hash と一致する
  3. ログのスコープ（tenant_id）が設定と一致する
- **チェックポイントを必須にする**: ログが存在するなら、チェックポイントなしでは実行できません。照合に失敗した場合も、その時点で止まります（fail closed）。
- **ログは暗黙には作らない**: `run` はログを作りません。ログがない、または空のファイルは「未初期化」として拒否します。新しいログを作れるのは `kodis audit-init` だけで、既存のファイルは上書きしません。
- **`audit-verify` は読み取り専用です**。`-checkpoint` を渡さなければ、末尾の削除を検査していないことを明示的に表示します。

## 復旧（`kodis audit-recover`）

有効なチェックポイントを失った場合の、明示的な手続きです。

- 理由（`-reason`）の入力と、log_id の先頭12文字の手入力を求めます。
- 確認が取れなかった場合は `recover-refused` レコードを残します。これは NotBefore を動かしません。
- 復旧すると `recover` レコードを追記します。このレコードには、それ以前の seq と head を「外部の基準では検証されていない」範囲として記録します。ログを開くときに、理由が空でないこと、記録された seq と head がチェーンと一致することを検証します。
- **復旧時刻（および初期化時刻）より前に発行された承認は、台帳が拒否します。** 削除された claim を、その時点で有効だった承認で使い回されるのを防ぐためです。判定するのは次の2か所です。
  - `Ledger.Claim(planHash, approvalIssuedAt)`: claim を記録するときに、同じロックの中で判定します。
  - `Ledger.Guard(approvalIssuedAt, fn)`: Executor は、Action ごとの書き込みをこの中で実行します。台帳はロックを取って判定し直し、ロックを持ったまま書き込みを行います。そのため、書き込みの途中に `Recover` が割り込むことはできません。Action と Action の間に復旧が起きた場合は、残りの書き込みが拒否されます（結果は `partial` になります）。すでに書き込んだ Action は元に戻しません。
- init と recover レコードの時刻は、それより前のどのレコードの時刻よりも前であってはいけません。満たさないログは開けません。NotBefore はそれらの時刻の最大値です。そのため、後から追記したレコードで NotBefore を過去に戻すことはできません。
- 復旧しても、削除されたかもしれない claim は戻りません。

## 保証できること

- 最後に照合したチェックポイントより前（その seq まで）のレコードが、削除・改変・並べ替えされていないこと。
- 別のログや作り直したログを、元のログの代わりに使われていないこと。log_id の不一致で検出します。
- 初期化または復旧より前に発行された承認で、実行されないこと。

## 残るリスク（保証しないこと）

1. **最後のチェックポイントより後ろのレコードの削除は検出できません。** 削除された中に claim が含まれていると、台帳から消え、同じ Plan を**新しい人間の承認で**再び実行できます（テスト `TestTruncationAfterCheckpointAllowsReexecution` で、この挙動を明示しています）。
2. **古いけれど正当なチェックポイントを渡された場合も、1 と同じです。** チェックポイントに署名しても、これは防げません。
3. **チェックポイントの信頼性は、保管先の独立性に依存します。** 同じマシンの同じユーザーが書き換えられる場所（別のファイルや別のディレクトリ）に保管しても、分離にはなりません。別の OS ユーザー、追記しかできない外部ストレージ、紙やチャットへの記録など、ログを書く主体とは別の主体に保管してください。
4. **ログの作り直しは、kodis 単体では検出できません。** ログを削除して `audit-init` を実行すれば、新しいログを作れます。検出できるのは、運用者が保管しているチェックポイントの log_id と照合した場合だけです。
5. **復旧しても、二重実行を完全には防げません。** 復旧前に発行された承認は無効になりますが、復旧後に新しい承認を得れば、claim が消えた Plan をもう一度実行できます。
6. **台帳はログごとに独立しています。** 別の `-audit` パスで新しいログを使うと、台帳は共有されません。古い承認は使えませんが（新しいログの初期化時刻より前に発行されたものになるため）、新しい承認で同じ Plan を実行できます。
7. **時刻はローカルの時計に依存します。** 承認の期限と、台帳での NotBefore の比較は、システムの時計を使います。時計を操作できる者は、これらの制約を回避できる可能性があります。逆に、時計が最新のレコードより過去に戻ると `Recover` は失敗します（安全側に倒した結果の運用上の制約です）。
8. **排他ロックは同じホスト内でしか効きません。** `flock` は開いた inode に対するロックです。親ディレクトリを書き換えられる者は、ファイルを差し替えられます。
9. **承認の記録は監査ログの中にあります。** ログを読める者は、有効期間内の承認を取り出せます。CLI は外部から承認を受け取らないので、CLI 経由では必ず新しい人間の承認が必要です。ただし Executor をライブラリとして直接呼べる者は、ログを書き換えて claim を消せば、取り出した承認を期間内に再利用できます。
10. **`Ledger` の別の実装は、この判定を省略できます。** `Claim` と `Guard` が承認の時刻を判定することは、型では強制できません。インターフェースの約束事として守られることを前提にしています。リポジトリ内の実装（`audit.Log` と `execute.MemoryLedger`）は、どちらも判定を行い、テストで確かめています。
11. **対象システムの状態による再実行防止は、前提にしません。** 実際のサービスでは、version の照合（CAS）で再実行が止まる場合があります。しかし KODIS はそれを安全性の前提にしていません。現在の mock は実行のたびにフィクスチャから作り直すので、状態による防止は働きません。

## 運用上の推奨

- 実行するたびに、表示されたチェックポイントを、ログとは別の主体が管理する場所に保管する。
- 実行の前に、保管しているチェックポイントの log_id が、使おうとしているログの log_id と一致することを確かめる。
- `audit-recover` は、チェックポイントを本当に失ったときだけ使い、その理由を残す。復旧した後に、それまでに実行済みの Plan をもう一度承認しないよう、Plan の内容と監査ログを確認する。
