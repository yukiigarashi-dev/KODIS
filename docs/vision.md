# KODIS のビジョンとスコープ（案）

この文書は、KODIS が最終的に目指すものと、そこに至る段階、各段階でやること・やらないことを定める。設計や優先順位の判断で迷ったときは、この文書に立ち返る。変更するときはユーザーの承認を得る。

## 目的

セキュリティの専門家がいない中小企業が、安全にセキュリティを改善できるようにする。

- 最終的な目標は、専門家（コンサル）がいなくても、診断から変更、検証までを安全に自動で行えること。
- ただし、変更には常に**顧客による同意（人間の承認）**を必要とする。承認そのものをなくすことは、設計原則の変更として別途判断する。

## 現在地

MVP。模擬の Entra テナントに対して、Conditional Access ポリシーを1つの方向にだけ変更する（`disabled` → `enabledForReportingButNotEnforced`）。MVP で実証しているのは、Entra の機能ではなく、領域によらない「安全に変更するための核」である。

- Plan は未信頼の入力として扱う
- 判定は I/O を持たない policy で行う
- 承認を Plan のハッシュに束縛する
- 書き込み直前に CAS で事前条件を確かめる
- 状態を独立に読み直して Verify する
- 監査ログとチェックポイント

## 利用者と役割

当面の利用者は、中小企業を支援するコンサル（または MSP）とする。中小企業の担当者が自分で使うことは、最終的な目標として残す。

| 役割 | 担う判断 | 例 |
|---|---|---|
| コンサル（運用者） | 技術的な妥当性。診断の実行、Plan の作成とレビュー、実行 | KODIS の CLI を操作する人 |
| 顧客（承認者） | 業務上の同意。「この変更をしてよい」 | 顧客企業の責任者 |

この分担から、次のことが必要になる。

- **承認者と実行者を分ける。** 顧客の承認なしに、コンサルが単独で変更を実行できないようにする。
- **顧客が判断できる承認の材料を出す。** 何が変わるか、誰に影響するか、どう戻すかを、専門用語に頼らずに示す。承認の材料は Plan のハッシュに束縛する（説明と実際の変更が食い違わないようにする）。
- **複数のテナントを扱う。** 設定、監査ログ、チェックポイント、承認の鍵を、顧客ごとに分ける。

## 基本方針: 読むのは広く、書くのは狭く

- **診断（Inspect / Evaluate）** は読み取り専用で、価値の大半はここにあり、リスクも小さい。対象を広げるときは、まず診断から広げる。
- **変更（Execute）** は、許可リストに1つずつ操作を足す。ある操作を許可リストに加えてよいのは、次をすべて満たす場合だけとする。
  1. 書き込み直前の事前条件の照合（CAS、またはそれと同等の条件付き書き込み）が、対象システムで成り立つ
  2. 変更後の状態を、Executor とは独立に読み直して検証できる
  3. 影響範囲を事前に限定できる
  4. 管理者自身が締め出されるような変更を、policy で拒否できる（Entra の break-glass の除外に相当するもの）
  5. 元に戻す手順が定義されている
- 満たせない領域や操作は、診断と推奨だけにとどめる。たとえば、API のない NW 機器や、管理接続が切れると遠隔では戻せない変更が該当する。

## 段階

各段階の終わりで、この文書を見直す。

### 段階1: Entra / M365 の診断と推奨（次に取り組む）
- 読み取り専用の診断モード。Inspect と Evaluate だけを行い、レポートを出す。書き込みの経路を持たないことを archtest で強制する。
- Entra / M365 の評価ルールを増やす。Conditional Access を使えないテナント（ライセンスの不足が想定される）向けのルールを含める。例: Security Defaults が無効で、Conditional Access もない。
- 顧客に渡せる形式のレポート。所見、重要度、推奨する対応、その根拠を含める。
- 抽象化はしない。Entra / M365 に特化してよい。

### 段階2: 限定的な変更（コンサルが運用し、顧客が承認する）
- plan / approve / execute を分割し、承認者と実行者を分ける。信頼できる承認の鍵を複数持てるようにする。
- 複数のテナントを扱う。
- 顧客向けの承認の材料を出す。
- 部分的に失敗したときの戻し方を設計する。
- 許可リストに加える操作は、上の5つの基準で1つずつ判断する。

### 段階3: 抽象化と、対象領域の拡大
- 2つ目の領域の adapter を、読み取り専用で作る。対象の候補は、ほかの SaaS、NW 機器の設定の書き出し、端末管理。汎用の抽象（対象と操作の型）は、この段階で初めて作る。
- 安全に変更するための核（policy、承認、execute、verify、audit）は、領域によらず共通にする。

### 段階4: 自動化の拡大
- コンサルの技術的な判断を、評価ルールと policy で置き換えていく。
- 顧客が自分で使えるようにする（承認の材料、操作の手順、失敗したときの案内）。
- 顧客による同意としての人間の承認は残す。

## 当面やらないこと

- **実テナント・実 Graph API への接続。** 段階1で実際の顧客を診断するには、実テナントからの読み取りが必要になる。しかし、これは CLAUDE.md の絶対ルールの変更にあたる。行う前に、脅威モデル、必要な権限の範囲（読み取りのみ・最小限）、認証情報の扱いを決め、ユーザーの承認を得る。それまでは、合成したフィクスチャだけを使う。
- **LLM の導入。** 導入する場合も、Plan は未信頼の JSON として、同じ検証経路を通す。
- **2つ目の adapter を作る前の抽象化。**
- **NW 機器や端末への書き込み。**
- **承認を省略する仕組み。**

## 未決事項と、確認していない前提

- **Conditional Access のライセンス。** Conditional Access には Entra ID P1 が必要で、Microsoft 365 Business Basic や Standard だけのテナントでは使えない、という前提を置いている。これは公式ドキュメントで確認していない。
- **実 Graph API の条件付き書き込み。** Conditional Access ポリシーの更新が、ETag と If-Match による条件付きの書き込みに対応しているかは確認していない。対応していなければ、段階2で Entra に書き込む操作は、上の基準 1 を満たさない。
- **顧客から承認を受け取る経路。** 顧客が CLI と鍵を扱う前提にするか、別の経路で署名を受け取るか。
- **レポートの形式と言語。**
- **顧客ごとの分離の度合い。** 同じホストで複数の顧客を扱うことを許すか。
